1 · Why this exists

The suite could only ever answer half a question. Every corpus was attacks, every metric was detection, and nothing measured what a guard costs. Under that framing the optimal guard is one that blocks everything: 48 of 48 attacks caught, nothing got through, a clean report and a green build.

That is not a hypothetical failure mode. aisg probe shipped with 48 cases, all of them attacks. A guard returning BLOCK unconditionally scored perfectly against it. Nothing in the repository could distinguish a good guard from a broken one, because the only question being asked was did anything get through.

What was impossible before this work: answering should I turn this guard on? That question needs three numbers — what it catches, what it breaks, and what it costs — and the project produced exactly one of them. The first run of the new tooling found that the default prompt-injection guard blocked 14% of legitimate traffic, that the eu_high_risk preset had never been loadable, and that the same guard under that preset cost 5.7 seconds per request while silently swallowing the error that caused it.

The framing is documented in CLAUDE.md and the README; this document explains the mechanism.

Key takeaways

  • An attack-only corpus makes “block everything” the winning strategy. That is a property of the measurement, not of the guards.
  • A guardrail is a trade: detection bought with latency and with false positives. The project priced neither.
  • Everything below follows from adding the second and third numbers.

2 · The system, and where the work lands

Fig. 1 — One corpus, two harnesses. aisg probe (grey, pre-existing) tests somebody's running service and can only read the reply; aisg measure runs the guards in-process where the verdict is exact. The lint rules and their bench/ harness share the Profile contract but are omitted here — they measure static analysis, not the request path.

Key takeaways

  • The benign corpus is the only genuinely new input; everything else is a consumer of it.
  • Black-box and white-box answer different questions, and neither replaces the other.
  • Profile is the join: measured once, read by the gate and by CI.

3 · M The measurement layer

3.1 · Goal

Produce, for one guardrail configuration, the three numbers that decide whether to deploy it: how much of the attack corpus it catches, how much legitimate traffic it breaks, and how much latency it adds at p50 and p99. The output has to be trustworthy enough to gate a build on, which means every verdict must be exact rather than inferred, and every number must be attributable to a single guard.

3.2 · Data flow

Fig. 2 — A case is classified by the guard's action and, for benign cases, by whether must_survive text is still present. Redaction is deliberately not a break. The pipeline assembly is omitted: guards are measured alone, never through the chain.

3.3 · How the data moves and transforms

The benign case declares what it tempts and, when the payload contains text an application genuinely needs, what must survive. There is no detector — a benign case has no “attack succeeded” marker to look for.

The classification is a single branch. Everything hinges on kind, and the benign side judges two exact conditions rather than one inferred one.

The thresholds judge only what has been measured. An unmeasured field cannot fail, which is what keeps “we have not looked at this yet” from reading as “this is broken”.

3.4 · Decisions, and why

  • ①Benign cases are adversarially benign, not small talk. Neutral chit-chat proves nothing about over-blocking. Every case is drawn from the same seed pattern as an attack — support traffic carrying an order number, a security engineer asking how to prevent injection, a moderation team quoting the phrase they filter. Rejected: sampling real production logs, which nobody has and which would carry real PII.
  • ②White-box, not another HTTP probe. Over HTTP you cannot distinguish a guard blocking a request from a model politely declining. In-process, blocked, passed and sanitized_output are facts. Cost: it measures your configuration, not your deployment — a proxy, a rate limiter or a gateway in front of the app is invisible here.
  • ③Guards are measured in isolation. A sequential pipeline short-circuits on the first block, so guards behind it would never see the payload and would score a spurious zero. Cost: interaction effects are not measured — a redaction chain that only works in order is not exercised.
  • ④None means unmeasured and still fires. Silencing a guard requires evidence; gating everything unmeasured would mute the suite on day one. Cost: an unmeasured guard is indistinguishable from a good one at the gate, so the reports label it explicitly rather than leaving the reader to assume.
  • ⑨Latency has no default cap. 200 ms is unremarkable in a batch job and fatal on an interactive path, so a universal limit would be wrong for somebody. The number is always reported; enforcement requires --max-p99-ms. Cost: a slow guard ships silently unless an operator opts in, which is why CI sets a budget explicitly.
  • ⑥A fresh context per case. The pipeline threads one dict through a request, and PII token maps and tool-session counters live in it. Sharing it across measurements would leak state between unrelated cases.
  • ⑦A guard that raises is reported, never fatal. A judge without credentials must not abort the run, and must not be scored as if it passed — it is reported as unavailable.
  • ⑧Redaction is not breakage. A guard that masks an email and lets the request through has done its job. Only a BLOCK, or the loss of declared must_survive text, counts against it.

3.5 · For a scalable system

The real ceiling is the corpus, not the code. 48 attacks and 42 benign cases are a smoke test: they detect a guard that is catastrophically noisy, and they cannot estimate a false-positive rate to better than roughly ±2 percentage points. A guard measured at 2% FPR here could plausibly sit anywhere between 0% and 7% on real traffic.

The upgrade path is per-deployment corpora rather than a bigger shipped one: the corpus loader already takes a --families filter and the YAML schema is stable, so an operator can add their own benign file drawn from their own traffic. The measurement is linear in cases × guards and runs in well under a second for the shipped set, so corpus growth is cheap until judge-backed guards enter the mix, where each case becomes a network call.

3.6 · Security

This layer has no trust boundary of its own — it runs locally, holds no credentials, and reaches no network. That is the point of separating it from aisg probe, which does cross a boundary and therefore refuses any non-loopback target without --i-have-authorization.

The one hostile input is the corpus itself: load_corpus() parses YAML shipped inside the package with yaml.safe_load, and payloads are only ever passed to guards as strings — never evaluated, never interpolated into a shell or a template. An operator adding their own benign corpus should treat it as they would test fixtures, and in particular should not paste real customer traffic into a file that will be committed.

Key takeaways — measurement layer

  • The benign corpus is what stops “block everything” being a passing grade.
  • In-process measurement buys exact verdicts at the cost of measuring the config, not the deployment.
  • Unmeasured is a reported state, never a silent pass.
  • The corpus is a smoke test, not a population estimate — it is sized to catch disasters, not to rank near-equal guards.

4 · C The corrections it forced

4.1 · Goal

Act on what the first measurements said, and leave behind a mechanism that prevents the same regressions returning. Three findings mattered: the default injection guard was unusable for its own audience, the strictest shipped preset could not be loaded at all, and the flagship integration was silently not sanitizing anything.

4.2 · Data flow — the FastAPI body rewrite

Fig. 3 — Why the old middleware silently failed. Mutating request._receive changes an object call_next does not consult; wrapping receive at the ASGI layer changes the only channel the application can read from. Response-side buffering is omitted for clarity — it follows the same pattern in reverse.

4.3 · How the data moves and transforms

The replacement hands the application a receive callable it cannot bypass, and corrects content-length to match — omit that and the server truncates the body at the old length.

src/aisg/integrations/fastapi_middleware.py:155–177 — the rewrite the application actually readsC
body[self.input_body_key] = input_result.sanitized_output
rewritten = json.dumps(body).encode()

# Content-Length must follow the body, or the server truncates it. ⓑ
scope = dict(scope)
scope["headers"] = [
    (k, v) for k, v in scope.get("headers", []) if k.lower() != b"content-length"
] + [(b"content-length", str(len(rewritten)).encode())]

await self.app(scope, self._replay(rewritten), self._guarded_send(send, context))

@staticmethod
def _replay(body: bytes) -> Callable:
    sent = False
    async def receive() -> dict:
        nonlocal sent
        if sent:
            return {"type": "http.disconnect"}
        sent = True
        return {"type": "http.request", "body": body, "more_body": False}
    return receive

The injection guard's false-positive problem was that it could not tell a phrase being used from one being discussed. Two cheap signals separate them — and one signal vetoes both, because indirect injection arrives precisely as quoted content.

src/aisg/modules/input/prompt_injection.py:169–189 — mention, use, and the veto that outranks bothC
def is_mention(content: str, span: tuple[int, int] | None) -> bool:
    if not span:
        return False
    # Indirect injection arrives as quoted content the model is asked to act on.
    # If anything in the message frames it that way, nothing here is a mention. ⓓ
    if _CONTENT_CUES.search(content):
        return False
    start, end = span
    for qs, qe in _quoted_spans(content):
        if qs <= start and end <= qe:
            return True
    window = content[max(0, start - _MENTION_WINDOW) : start]
    return bool(_DISCUSSION_CUES.search(window))

4.4 · Decisions, and why

  • ⓐRewritten as pure ASGI rather than patched. BaseHTTPMiddleware cannot reliably alter a request body across Starlette versions; the previous code was correct against an older contract and silently wrong against the current one. Rejected: pinning Starlette, which moves the failure to the user's dependency resolver. Cost: more code, and the response body is now buffered rather than streamed — see the recommendation on streaming.
  • ⓑcontent-length is rewritten in both directions. Redaction changes the body length. Leaving the header stale truncates the payload, which would have been a second silent corruption on top of the first.
  • ⓒA blocked request never reaches the route. The middleware responds directly. Anything less is not an inline filter — it is logging.
  • ⓓA mention is downgraded, never dropped. The finding stays in the result as a FLAG, so the behaviour remains observable and auditable; it simply does not block. And the content-processing veto outranks the quoted-span signal, because the corpus proved a real indirect injection was being downgraded by it — when the two disagree, the payload is treated as live.
  • ⓔspace_injection was removed rather than narrowed gently. Its pattern, \b[a-z]+(?: [a-z]+){3,}\b with re.I, matched any four English words — “what is the capital of france” fired it. It was the only advanced technique producing benign hits. Cost: four apparent catches, which were never detection, only a pattern that matches all prose.

The catch drop is entirely the space_injection removal. A test asserts that allowing security discussion produces identical verdicts on all 48 attack cases, so the false-positive fix cannot have traded detection for quiet.

4.6 · For a scalable system

The ceiling here is the buffered response. _guarded_send accumulates the whole JSON body before output guards run, which is fine for chat-sized replies and wrong for streaming: it converts time-to-first-token into time-to-last-token. There is no streaming path today, and no number in the README saying what that costs. The upgrade path is incremental output scanning over chunk boundaries, which changes what an output guard can promise — a guard that needs the whole response cannot run incrementally, so the API would have to distinguish the two.

_read_body also accumulates the request without a size limit, so a large upload passing through this middleware is held in memory once per request.

4.7 · Security

The middleware is the trust boundary: everything arriving on receive is hostile, and the code treats it that way — a malformed or non-JSON body is replayed untouched rather than rejected, so the middleware cannot be used to deny service to routes it was never meant to inspect, and a non-string message field is passed through rather than coerced.

The mention heuristic is a deliberate, bounded relaxation of a security control, and it is the part of this work most worth reviewing adversarially. An attacker who wraps a payload in quotes and prefixes “how do I prevent” gets a FLAG instead of a BLOCK. That was judged acceptable because the finding is still recorded, the content-processing veto covers the indirect-injection vector, and the alternative — a guard that blocks its own users — gets switched off entirely, which is worse. It can be disabled with allow_security_discussion=False.

No credentials pass through this layer. The judge-backed guards hold them, and the one measured failure mode there is a missing key producing seconds of latency with the exception swallowed at prompt_injection.py:381.

Key takeaways — corrections

  • The flagship integration silently sanitized nothing; the bug survived because the integration had no tests.
  • Mention-vs-use took the injection guard from 14% to 0% breakage with identical attack verdicts.
  • A pattern that matches all prose was scoring as detection.
  • The relaxation is bounded, observable and switchable — and is the right place to point a reviewer.

5 · Cross-cutting: Profile as the contract

Runtime guards and static lint rules are different objects measured by different harnesses, and they share one vocabulary. GuardrailBase.profile and BaseRule both carry a Profile, and both consult the same Thresholds, so “should this run by default?” has one answer shape regardless of what is being judged.

src/aisg/core/base.py:190–204 — the same gate for every guardM
profile: Profile = Profile()

def fires_by_default(self, thresholds: Thresholds | None = None) -> bool:
    # An unmeasured guard keeps running: silencing one needs evidence, and
    # gating everything unmeasured would mute the suite. ④
    return (thresholds or DEFAULT_THRESHOLDS).accepts(self.profile)

def demotion_reasons(self, thresholds: Thresholds | None = None) -> list[str]:
    return (thresholds or DEFAULT_THRESHOLDS).failures(self.profile)

The usage this was built to enable is a single command that fails a build:

.github/workflows/tests.yml — the ratchet ⑤C
- name: Measure the default pipeline
  # exits non-zero when any guard breaches a threshold, so a guard that
  # starts over-blocking or slows down fails the build instead of
  # quietly degrading.
  run: aisg measure --max-p99-ms 25

Key takeaways — the contract

  • One vocabulary for two kinds of thing, so the gate is not reimplemented twice.
  • The gate is dynamic, not snapshotted at import — an earlier draft cached it and silently gated the wrong set.
  • CI reads the same thresholds a developer does, so local and remote verdicts agree.

Discovered while writing this document:

  1. The measured profiles are not written down. aisg measure prints a paste-ready Profile(...) block and no guard class carries one, so every guard still reports as unmeasured at the gate. The numbers exist and the mechanism exists; they are not yet connected. Paste them, and re-run to confirm the gate agrees.
  2. Output guards are measured against the wrong corpus. toxicity_output inspects model responses, and the shipped cases are user input, so its catch rate is meaningless — the tool says so in a note rather than printing a grade, but the honest fix is a response corpus. Its benign and latency columns are valid today.
  3. Streaming is unaddressed and unpriced. Buffering the full response to filter it converts TTFT into total latency. Either add an incremental path or state the cost in the README with a measured number; silence is the one option that is not acceptable for a project whose thesis is that costs should be visible.
  4. The judge failure mode is expensive and silent. With llm_judge: true and no credentials, a single call measured 5686 ms against 11.7 ms with the judge off, because the exception is swallowed at prompt_injection.py:381. Accepted for now only because credentials are pending; it should fail loudly, or at minimum log once per process.
  5. _read_body has no size limit. The middleware buffers the whole request. Add a ceiling before this sits in front of anything accepting uploads.
  6. The corpus is a smoke test and should say so where it is consumed. 42 benign cases cannot estimate a false-positive rate to better than a couple of points. The report's disclaimer covers “not compliance”; it does not yet convey “not a population estimate”.
  7. Accepted, because: rate_limiter scores 0/48 and stays. The corpus contains no flood cases, so that number measures nothing about a rate limiter — removing it on that basis would be exactly the error this work exists to prevent.

Key takeaways — next

  • The loop is closed mechanically but not yet populated: measured numbers still need pasting onto the classes.
  • The two honest gaps are streaming cost and output-guard measurement; both need a number, not a fix.
  • One recommendation is explicitly declined, with the reason recorded.
