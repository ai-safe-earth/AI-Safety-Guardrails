1 · Why this exists

The previous document priced this package's own guards: what each one catches, what it breaks, what it costs. That machinery only works on a tree that already has aisg guards wired into it and a corpus to run them against. Aim it at somebody else's repository — a LangChain agent, a Node service with three MCP servers, a notebook that shells out on model output — and it has nothing to say. There was no way to answer the prior question: what can this agent already reach, and what evidence exists that anything stands between the model and that reach?

Two constraints made that question harder than a linter.

The first is that an audit is read by someone who will act on it, so it must never overstate. The tempting output — a score, a grade, a green tick — is exactly the output that gets pasted into a compliance deck. A tool that says "compliant" about an EU AI Act obligation is worse than no tool, because the classification is a legal determination the operator makes. So the report had to carry a vocabulary for where each claim came from, and had to be structurally incapable of producing a verdict.

The second is that the audit only helps if it runs where the code is. That means no install step it can perform itself, no network call it initiates, no model in the loop — and a way to reach whichever agent host the reader happens to use. Hence a deterministic CLI (aisg audit) that does the finding, and a thin agent skill that does the explaining, shipped inside the wheel and copied into Claude Code, Codex, Cursor and Gemini skill directories by aisg skill install.

What landed: 46 rules ordered by blast radius, a three-bucket evidence model, eight adapters for scanners that are already installed, a fingerprint baseline, four renderers, and a five-phase skill that never edits a permission file without showing the diff first. The audit now runs against this repository in CI on every push.

Key takeaways

  • Measurement answered "is this guard worth its cost". This answers the earlier question: "what is there to guard, and what proof exists".
  • The hard requirement is honesty about provenance, not coverage: every claim carries where it came from.
  • Deterministic tool + thin skill, because the skill has to survive being copied to a host that is not Claude Code.

3 · E The evidence pipeline

3.1 · Goal

Turn an arbitrary repository into a structured description of its AI surface — which files call a model, which tools an agent can invoke, which MCP servers are configured, where secrets sit, what CI runs — using only file reads, and without ever being wrong in the silent direction. Every file the walker declines to read, every Python file the AST layer cannot parse, every scanner that is not installed becomes a visible UnknownItem. The pipeline's contract is that it never returns a quiet nothing.

3.2 · Data flow

The .env* re-inclusion sits inside the gitignore check, not around it: it is the one deliberate divergence from git semantics. Deliberately omitted: the two read-only git subprocess calls (git_meta, file_age), which affect only report metadata.

3.4 · Decisions, and why

  • ①.env* is walked even when .gitignore excludes it. Rejected: follow git exactly. On a developer machine the highest-blast-radius credentials in the tree live in a gitignored .env; obeying git would have made them invisible while the report implied secrets were covered. The cost is that the audit reads a file the developer deliberately kept out of version control, so would_ignore is preserved separately and every such finding renders (gitignored). Redaction is unconditional (see ⓔ), which is what makes this safe rather than reckless.
  • ②Three file classes, not one. A README containing pip install foo is not a supply-chain finding, and a docs page quoting a host's permission-bypass flag is not an over-grant. The rejected alternative — run every table everywhere and let precision sort it out — has no precision to sort it with (see ⓖ). The escape hatch matters as much as the rule: a prompt template is a .md file by extension, but PII in it ships to the model on every request, so PII_FILE_GLOBS overrides the class.
  • ③Every failure is a row, not an exception. A file that will not decode, a Python file that will not parse, a directory that will not open: each becomes an UnknownItem with a how_to_resolve string. The ceiling is that UNKNOWN is a flat list — on a large monorepo with a vendored directory it can be longer than the findings, and nothing groups it. --fail-on-unknown <categories> exists so CI can treat "the scanners did not run" as a failure, which is the case that matters.
  • ④fail_open is stored apart from gates. If a swallowed guard call landed in gates, it would satisfy AUD-201's tool-gate join and an ungated irreversible tool would report as gated — a false clean on the single highest-severity rule in the P2 band. Keeping the two lists separate makes that impossible structurally rather than by ordering. The same fact then feeds AUD-802 as a finding in its own right, so nothing is lost by the separation.
  • ⑤Rules read files only through file_text. Rejected: let each rule open what it likes. That would let one rule silently escape the walk's exclude list, so a repository excluded from the scan could still be quoted in the report. The cache is a side benefit; the containment is the point.

3.5 · For a scalable system

The pipeline is single-process, single-threaded and holds the file list plus every hit in memory. On this repository (135 files enumerated, 70 of them Python) a full run with --no-external takes 7.4–8.0 s in-process on a Windows laptop, three runs — an order of magnitude more than the file count suggests, and worth knowing before pointing it at a monorepo. The real ceilings, in the order they will bite:

  • Hits are held for the whole run (ctx.hits), because rules query them by table late in the pipeline. A monorepo with a few hundred thousand matched lines will hold all of them. The fix is an index keyed by (table, unit) rather than a list scanned by hits_in, which is linear per call.
  • unit_of and file_text scan ctx.files linearly for every lookup. With 46 rules that is fine at 102 files and quadratic at 105.
  • The AST layer is Python-only. --deep python|none has no third value. For TypeScript and Go the audit is at grep depth plus whatever semgrep contributes if it happens to be installed — and the report says so, per language, in the UNKNOWN block. That is the honest position, not a workaround, but it does mean a Node agent gets a materially weaker audit than a Python one.
  • The call graph is depth-3 and resolved by bare name. Dynamic dispatch, registries and decorators are not followed. This is listed on AUD-301 as a known failure mode rather than hidden.

3.6 · Security

The audit reads a hostile tree: the whole point is that the target may be compromised, careless, or both. The trust boundaries it holds:

  • Target content is never executed and never interpolated into a command. The only subprocess calls in the evidence pipeline are read-only git invocations, never with shell=True, never with check=True, always with a timeout.
  • Every parser is a safe parser. yaml.safe_load, json, tomllib, ast.parse — nothing that evaluates. configs.py takes the further step of never regexing a config body: patterns are applied only to individual string values pulled out of a parsed structure.
  • Secret values never enter the returned objects. Env bindings and MCP env maps are reduced to a name plus a boolean saying whether the value was a literal. The value itself is not carried, so it cannot leak through a later rendering bug.
  • Snippets are redacted at construction. Evidence.__post_init__ calls truncate_snippet, which redacts then truncates — cutting first could expose a partial secret.
  • What is not defended: a target that plants a 2 GB file inside the size cap, or a pathological regex input, will make the run slow. There is no per-file time budget, only a per-adapter one.

Key takeaways — evidence pipeline

  • Read-only, safe parsers, no execution of target content, redaction at the point of construction.
  • Two divergences from the obvious behaviour, both deliberate and both visible in the output: .env* is read; a swallowed guard is not a gate.
  • Nothing fails silently — a rejection at any stage is a printed UNKNOWN row with a resolution hint.
  • The honest weakness is depth: only Python gets AST analysis, and the report says so per language.

4 · R Rules, buckets and the gate

4.1 · Goal

Turn the context into findings a human can act on in priority order, attach to each one where its evidence came from, and produce an exit code CI can gate on — without the tool ever being able to say the target is fine. Ordering is by blast radius, not by likelihood: AUD-101 (a host permission over-grant) outranks AUD-1001 (no system card) because the first one means an agent can already do anything on the machine.

4.2 · Data flow

4.4 · Decisions, and why

  • ⓐA rule exception is a row, not a crash. Rejected: let it propagate so bugs are loud. On a tool whose job is to audit unfamiliar trees, the loud version means one malformed package.json in a monorepo produces no report at all. The cost is that a systematically broken rule looks like a quiet UNKNOWN row rather than a test failure — which is why the rule registry does the opposite for imports: a rule module that exists but fails to import raises, because a silently vanished rule set is not partial, it is wrong.
  • ⓑNever install, never fetch. Rejected: uvx the missing scanner, which is what makes for a good demo. An audit that installs software is a supply-chain vector aimed at whoever runs it, and the audited tree gets a say in what is installed. The cost is that a fresh CI runner measures nothing — every scanner row is UNKNOWN (see recommendation 5). install_hint is text the report prints; nothing executes it.
  • ⓒMEASURED replaces ASSERTED at the same key. The alternative — keep both — inflates the count and lets a reader believe two independent sources agree when one is a strict upgrade of the other. Key is (rule id, file, line), so the replacement is conservative: an adapter finding one line away from ours produces two rows, which is the safe direction to be wrong in.
  • ⓓThe renderers are checked against their own banned vocabulary. Rejected: a review convention. Conventions do not survive a copy-edit six months later. The check scans only the renderers' fixed strings, never the target's text, so a comment in the audited repo cannot trip it — otherwise auditing a compliance library would fail the audit tool.
  • ⓔ--no-redact parses and then refuses. Rejected: omit the flag entirely. Someone who wants unredacted output will look for the flag; finding it, and being told why it will not work, is a better outcome than finding nothing and reaching for the JSON. Exit 2, so a script cannot ignore it.
  • ⓕExit 0 is named EXIT_OK, and a whole test bans the word one would rather use. Nothing under the audit directory may contain the obvious name for a zero exit, because that word in a report is a verdict. It reads as pedantry until you notice that every renderer, every docstring and every constant had to be written by someone who did not reach for it.
  • ⓖUnmeasured rules fire. All 46 are measured_precision = None, rendered [UNMEASURED]. Gating on unmeasured would mute the entire tool; assuming precision would be a fabricated number in a document whose entire premise is provenance. So: fire, and label. This is the same contract Profile carries for guards — see the previous document's cross-cutting section.

4.5 · For a scalable system

  • The exit code is one bit for 46 rules. --fail-on is a single severity threshold across every priority band, so a repository cannot say "fail on any P1, warn on everything else". On this tree that shows up as --fail-on high leaving 21 of 23 findings uncounted — correct for a library, wrong for a deployed agent. Per-band thresholds are the obvious next knob.
  • Adapter timeouts are per tool, not per run. Eight adapters at the default 120 s is a 16-minute worst case before anything is rendered, and there is no partial output.
  • The baseline is a flat fingerprint list. It does not record the rule set or the tool version that produced it, so a rule change that alters a snippet silently converts accepted findings into new ones. That is the safe direction, but it makes an upgrade noisy in a way nothing explains at the time.
  • Four renderers duplicate the same ordering and tagging logic. Adding a fifth means re-deriving [UNMEASURED] / [REPORTED] / (gitignored) placement a fifth time.

4.6 · Security

  • The adapter layer is the only place a process starts, and build_argv is pure — it is exercised in tests with process creation disabled, so a regression that shells out during argument construction fails immediately.
  • Argument construction never interpolates target content into a shell. Adapters build an argv list; there is no shell=True anywhere in the audit.
  • A scanner's raw secret value never reaches a finding. Adapter findings carry the file, the line and the scanner's rule name — not the matched token. This matters more than it sounds: gitleaks output contains the secret it found.
  • network is declared per adapter and copied into the result row, so a reader can see exactly which findings depended on a tool that talked to a remote service. pip-audit, npm audit, osv-scanner and promptfoo are true; the rest are false. The audit process itself opens no socket in any configuration.
  • promptfoo needs --run-evals because it may call model providers and spend money. Without the flag it is skipped_needs_flag and lands in UNKNOWN, not silently absent.
  • What is not defended: the scanners themselves. If semgrep on PATH is malicious, the audit runs it. The mitigation is that the audit never put it there.

Key takeaways — rules, buckets and the gate

  • Blast radius orders the rules; severity is never adjusted by confidence.
  • Three buckets and two labels ([UNMEASURED], [REPORTED Nd]) carry every provenance claim the report makes.
  • Two refusals are structural, not conventional: no unredacted output, and a renderer self-check against verdict language.
  • The no-install rule costs real coverage on a clean runner, and the report shows exactly what it cost.

5 · S The portable skill

5.1 · Goal

Put the audit in front of someone whose repository it is, on whichever agent host they use, with an agent that reads the report competently and changes code only with per-item consent. The skill must be the same artifact everywhere — a fork per host would drift, and the drift would be in the safety rules.

5.2 · Data flow

5.3 · How the data moves and transforms

Three copies of a skill in a repository is a drift problem waiting to happen, so the equality is mechanised rather than reviewed. The digest is over the sorted (relpath, content) stream with length prefixes, so a rename or a deletion changes it, not just an edit:

src/aisg/skills/__init__.py:76–86 — one number for the whole treeS
def skill_digest() -> str:
    """
    sha256 hex over the sorted `(relpath, content)` stream, so any changed,
    added, renamed or removed file changes the digest. Each entry is
    length-prefixed, so the stream has one unambiguous encoding.
    """
    digest = hashlib.sha256()
    for relpath, content in iter_skill_files():
        digest.update(f"{relpath}\0{len(content)}\0".encode("utf-8"))
        digest.update(content)
    return digest.hexdigest()

5.4 · Decisions, and why

  • ⓧOne canonical copy in the wheel, two committed mirrors. Rejected: keep the skill only under .claude/skills/ and package it from there — which inverts the dependency, making the wheel's contents a function of a Claude-specific directory. Rejected too: generate the mirrors at build time, since they would then not be reviewable in a diff. The cost is a sync step that is easy to forget, so sync_skill.py --check runs in the test suite and aisg skill diff --host all runs in CI. Every version bump must be followed by a sync, because the bootstrap pin lives inside the mirrored files.
  • ⓨAn unverified host location says so on stderr, every time. Rejected: drop the unverified hosts. A user on Codex would then have nothing, and would copy the directory by hand to a guessed path with no warning at all. Rejected also: mark them verified and move on — Host.__post_init__ makes that impossible without a source URL. The note names what the vendor page actually said, so the user can check rather than trust.
  • ⓩThe bootstrap tries three package runners and then stops. aisg on PATH, then uvx (which provisions Python itself, so it works on a machine with none), then pipx. If all three are missing it prints install options and exits rather than attempting anything clever. All three specs are pinned to the exact version — the tool that flags unpinned bootstraps in other people's repositories cannot ship one. Today those specs resolve to a 404, because nothing is published yet; that is the safe failure, and it is the reason the PyPI name had to be settled first (see STATUS.md).
  • ⓦThe skill is thin on purpose. The 93 lines of SKILL.md contain no detection logic; they say which command to run and how to behave around the result. Rejected: an agent that reads the code and reasons about safety directly, which is non-deterministic, unauditable, and produces a different answer on every host. A deterministic CLI plus a short procedure means the finding set does not depend on which model is driving.

5.5 · For a scalable system

  • Host locations are a hardcoded table with a build-time verification date. Six hosts today, checked 2026-09-02. Vendors move these directories; there is no mechanism that re-checks, only a verified flag that goes stale silently.
  • The version pin is duplicated across four scripts (audit.sh, audit.ps1, verify.sh, verify.ps1) and rewritten by sync_skill.py. A test asserts it matches pyproject.toml, so the duplication is caught rather than avoided.
  • Every skill file lives in the wheel, so the reference guides (apply/python.md, apply/go.md, …) grow the distribution. At 13 files that is nothing; a per-framework guide set would want a different packaging story.

5.6 · Security

  • aisg skill install writes exactly one directory — <host dir>/ai-safety-audit/. Host settings and permission files are never touched by the installer. A destination that exists and differs is refused (exit 1) unless --force is passed.
  • --host all only creates directories for hosts already present, apart from claude and agents. Installing into .cursor/ on a machine that never ran Cursor litters the repository and, worse, creates a plausible-looking path that nothing reads.
  • The skill's rule 4 is the real control. An agent with write access to .claude/settings.json can grant itself permissions; the rule requires a shown diff and a specific approval for exactly those files, restated as a permission change before the ask.
  • The report is data, not instructions. Findings quote the audited repository, which may contain text designed to be read by an agent — the audit's own corpus is full of such text. The skill's procedure treats report content as evidence to present, and every action it takes needs a human yes.

Key takeaways — the portable skill

  • One artifact, digest-pinned, mirrored into the repo so drift shows up in a diff and in CI.
  • Unverified host paths ship with their uncertainty rather than being dropped or laundered.
  • The intelligence stays in the CLI; the skill contributes consent rules and an order of operations.
  • Nothing that writes, and nothing that costs money, happens without a separate approval.

6 · Cross-cutting: the fingerprint as the join key

Three separate mechanisms need to agree on when two findings are "the same one": the baseline diff, the CI gate, and a human writing down why a finding is acceptable. A line number cannot be that key — adding an import above a finding would resurrect every acceptance below it. So identity is content-shaped, and deliberately blurry in one direction:

src/aisg/devtools/audit/model.py:336–349 — identity that survives renumbering and renamingER
def _norm(snippet: str) -> str:
    """Collapse whitespace and strip digits from identifiers of three or more characters.

    `foo1` and `foo2` normalise to `foo`, so a renamed local or a renumbered line does
    not create a "new" finding. Pure numbers such as `4096` are not identifiers and
    survive intact.
    """
    return _IDENT_RE.sub(_strip_ident_digits, _normalise_ws(snippet))

def fingerprint(rule_id: str, relpath: str, snippet: str) -> str:
    """Stable 16-hex-char identity of a finding across runs and line renumbering."""
    payload = f"{rule_id}|{_posix(relpath)}|{_norm(snippet)}"
    return hashlib.sha1(payload.encode("utf-8")).hexdigest()[:16]

Note what is in the key: the rule's display id (so AUD-107/inert never collides with AUD-107) and the POSIX relative path. Move the file and the finding is new again — correct, because a finding accepted in a test fixture is not accepted in production code. Note what is out: the line, and digits inside identifiers.

The acceptance list is where this gets its point. A baseline may carry an accepted array alongside fingerprints, and a reason is mandatory:

There is a recursive twist worth stating, because it is not obvious and it constrains how these reasons are written: the baseline file is itself scanned by the audit. It is not on the exclude list, and read_report skips it only in its capacity as a report. So a reason that quotes the literal which produced the finding reproduces that finding, in the file that accepts it. A test — test_committed_baseline_does_not_reproduce_the_findings_it_accepts — pins this. Every reason above describes its evidence without quoting it.

Put together, the gate this repository runs on every push is one line, and every piece of it has a reason to be there:

Key takeaways — the join key

  • Identity is sha1(display id | posix path | digit-stripped snippet): stable across renumbering, unstable across moving a file, which is the correct pair of behaviours.
  • An acceptance without a reason is rejected at load time — the file cannot be used as a silent suppression list.
  • The baseline is audited too, so a reason must describe its evidence without quoting it.
  • The summary line is the product: counts per bucket, and how many findings the threshold did not count.

Discovered while writing this document:

  1. AUD-801's anchor lands on re-exports, not on wiring. It fires ten times here, and its evidence lines are src/aisg/modules/input/__init__.py:1, src/aisg/integrations/__init__.py:6, src/aisg/__init__.py:57 — import statements. The rule's own known-failure-mode text predicts this ("anchored on the first by path, so the anchor may be a re-export"), which is honest, but a reader opening __init__.py:1 learns nothing about the guard. When pydeep resolved a class definition for the guard, anchor there and demote the imports to also evidence. Cheap, and it makes ten of this repository's twenty-three findings actionable.
  2. The audit independently re-derived the previous document's open recommendation. Recommendation 1 there was "the measured profiles are not written down". AUD-801 now says the same thing from the other direction, ten times, without knowing about the document — no Profile(...) exists anywhere under src/aisg/modules/. Two independent mechanisms agreeing raises this from a note to a task: run aisg measure, paste the blocks, and watch ten findings become fixed in the baseline diff. It is also the cleanest available end-to-end test of the fixed path, which nothing currently exercises on a real change.
  3. Prose citations of this codebase have drifted, and this is the one place fingerprints do not help. The swallowed judge failure is cited three ways: CLAUDE.md says prompt_injection.py:123 (now a comment about mention-vs-use), the previous document says :381 (correct — the except Exception: pass), and AUD-802 anchors :353 (the try: opening the block). Fix the CLAUDE.md line, and prefer PromptInjectionGuard._llm_judge_check over a number in prose that no test pins.
  4. Every external-tool row is UNKNOWN on every CI run, permanently. The gate passes --no-external because the runner has no scanners and the audit will not install any (ⓑ) — so eight of nine UNKNOWN items are "skipped by --no-external", every time, and the MEASURED bucket has never been non-zero in CI. Two honest options: add a step that installs gitleaks and pip-audit on the runner (the runner installing them is not the audit installing them, and the boundary is exactly the one ⓑ draws), or state in the workflow comment that the gate is regex-only by design. The current state reads as an oversight and is not one.
  5. The project that ships aisg init has no system card. AUD-1001 fires on this tree. Either run aisg init --defaults — which also gives the audit's own system-card reader a real input to exercise — or accept it with the reason that a library is not a deployed AI system, which is already the reasoning behind the AUD-107 acceptance.
  6. The audit has no rule for unbounded buffering of untrusted input. The previous document's recommendation 5 (_read_body in the FastAPI middleware reads the whole request with no ceiling) is still true, and the audit cannot see it: no AUD rule covers resource exhaustion on the ingress path. Either add one to the P1 band — an ingress read with no size cap is blast radius, not hygiene — or record availability as an explicit non-goal in the rule registry, so the gap is a decision rather than an omission. Right now a reader could reasonably infer from a clean P1 band that ingress was examined.
  7. HTML documentation is classified as code, so the doc demotion never applies to it. _DOC_EXTS (discover.py:124) is {.md, .markdown, .mdx, .rst, .txt}; anything else that is not a config language falls through to code and gets every table. Controlled test — the same sentence, quoting a host permission-bypass flag, written twice: docs/a.md → AUD-101/docs low, docs/a.html → AUD-101 critical. Writing this document is what surfaced it: the paragraph explaining decision ② quoted the flag it was describing, and the audit reported it at CRITICAL against a file in docs/explain/ (the sentence has since been rephrased, so the tree is clean). This is the same self-reference the baseline's reason field already guards against, one directory over. Add .html and .htm to _DOC_EXTS — a rendered HTML page is prose by every criterion the class already uses, and the PII_FILE_GLOBS override still catches an HTML prompt template.
  8. Accepted, because: the baseline accepts all 23 findings, which means the gate can only ever catch new ones. That looks like a rubber stamp and is not: each entry carries a reason, the reasons are load-bearing enough that a test checks they do not reproduce their own findings, and the summary line prints 23 unchanged on every run where the count is visible. Lowering --fail-on would produce a red build that says exactly what the current green build already says.

Key takeaways — next

  • The engine and the skill are complete and gated; what is missing is numbers — rule precision and guard profiles, both waiting on labelling rather than on code.
  • Two findings here come from the audit auditing itself: an anchor that points at imports, and a system card the tool can generate and does not have.
  • One gap is in the rule set rather than in a target: nothing covers unbounded ingress, and a clean P1 band currently implies otherwise.
  • Writing this document tripped the audit at CRITICAL, which is how the .html-is-code classification was found. The self-reference hazard is not confined to the baseline file.
  • The MEASURED bucket has been empty in CI since the gate landed. That is a defensible choice, but it should be stated where the choice is made.
