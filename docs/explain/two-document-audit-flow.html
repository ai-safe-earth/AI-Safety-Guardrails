1 · Why this exists

Before this work, aisafe audit could produce a list. A list of findings, ordered by blast radius, in four formats. What it could not do was answer the three questions an owner asks after the list:

  1. Where in my system is this? A finding named a file and a line. Nothing placed it on a picture of the system, so twenty findings read as twenty unrelated problems.
  2. Can this package fix it, and fully? Each rule had a recommendation in prose. Nothing said, in a form an agent could act on, whether wiring an aisafe class is the control or only a partial one — and what it leaves open.
  3. What changed since last time, and why is this one still here? The baseline was a list of fingerprints (16-character ids for a finding). A fingerprint in it silenced the finding. Nothing recorded why, so an accepted risk and a forgotten one looked the same.

The fix is a two-document flow. Document 1 draws the user's system and lays out a plan. The skill walks the plan one row at a time, with approval. Document 2 says what is no longer reported, what is left, and in the operator's own words why each remaining item stays. STATUS.md holds the full change list (docs/STATUS.md, "Landed — the two-document audit flow"); this document explains the mechanism.

Key takeaways

  • The audit went from "a list of findings" to "a before and an after document of your system".
  • Three new pieces: a machine-readable package block per finding, a baseline that stores reasons, and a skill that walks the plan between the two documents.
  • The JSON stays the source of truth. The html is a rendering of it and adds nothing.

3 · D The document: package block, map, plan

3.1 · Goal

Give every finding a place on a picture of the user's system, and a row in a plan that says who does the work: this package, the user, or the user with an explicit approval because the file is sensitive. The plan must be decidable from data, so the agent in phase 3 reads a field instead of interpreting prose.

3.2 · Data flow

Fig. 2 — One finding, two destinations. The map placement depends only on the rule id; the plan row depends on the rule's package block, the file's language and whether the path is protected. Nothing here reads the finding's prose.

3.3 · How the data moves and transforms

It starts on the rule. Each rule declares what the package can do about it, and the constructor refuses a block that offers something without saying what it leaves open:

3.4 · Decisions, and why

  • ①same_control is a bool, and leaves_open is required text. Rejected: a coverage score ("this guard covers 70% of AUD-301"). No one has measured that number, and this project's rule is that an unmeasured figure is never typed in. A bool plus a sentence says what is true: either wiring the class is the control, or it is something else that helps. The text is rendered every time the symbol is offered, so a partial fix is never shown without its gap. Cost: the text is hand-written per rule, and can drift from the code it describes — mitigated by generating controls.md from the registry (scripts/controls_md.py, test-pinned).
  • ②"Who" is computed at render time, not declared by the rule. The same rule can be package work in agent.py, the user's work in agent.ts, and an approval-gated edit in .github/workflows/ci.yml. A rule-level field could not say all three. A protected path overrides everything: permission files, CI pipelines, .env* and .pre-commit-config.yaml always need the user to approve the specific diff. Cost: the derived value is not in the JSON; only its inputs are (see recommendation 2).
  • ③A document, not a dashboard. ASCII only, no severity colour (order already carries priority), [UNMEASURED] on every map box, the disclaimer above the figure, no script. Rejected: an interactive page. It cannot be diffed in a pull request, and the audit would then have to walk its own JavaScript. The html carries nothing the JSON does not; the footer says the JSON is authoritative.
  • ④Ten fixed boxes, exact cover, and a box for what does not fit. SUBSYSTEM_OF_RULE maps every rule id to one of ten subsystems; a test fails if a rule is added without a row. UNKNOWN items that name no rule, and ids outside the registry, go to "Not attributed / UNKNOWN", which is always drawn even at zero. Rejected: drawing the discovered architecture (services, units). That would be more faithful, and far harder to make deterministic. Cost: a system with two agents gets one "Tools and actions" box.

3.5 · For a scalable system

  • The plan table has one row per finding, uncapped. Subsystem sections cap at MAX_FINDINGS_PER_SECTION = 12 and facts at MAX_FACTS = 8, with "+N more in the JSON"; the plan does not. On the first AdalFlow run that would have been 563 rows. The precision round's grouping (df67200: one decision, one finding) took it to 49 — grouping, not a cap, is the scaling mechanism, and STATUS.md lists AUD-602, AUD-605 and AUD-106 as the next rules to group.
  • The map does not grow with the system. A monorepo with five services gets the same ten boxes. The upgrade path is one map per unit (the inventory already has units), not a bigger picture.

3.6 · Security

  • Everything on the page came from a hostile repository. File names, snippets, model ids and inventory labels are attacker-controlled text. Every value goes through _esc (html.escape(quote=True), then ASCII-forced) at html.py:378–380; the page has no script to inject into. Secret-shaped snippets are redacted before any renderer sees them, and --no-redact is refused.
  • The page lands in the audited tree. Line 1 is OWN_HTML_MARKER_LINE, so the next walk skips it — and names it (see ⓔ). Without that, a report quoting a finding would reproduce the finding on the next run.

Key takeaways — the document

  • Each finding now says, as data, whether the package is the control, a partial help, or nothing — and what it leaves open.
  • Who does a row is derived from the rule, the file's language and whether the path is sensitive. The agent reads the field; it does not interpret prose.
  • Ten fixed boxes make the map deterministic, and cap how much architecture it can show.

4 · B The baseline as a record

4.1 · Goal

Turn the baseline from a silencer into a record. It should say which findings existed at the survey, which ones the operator chose to keep and why (in their words), and let a later run name what is no longer reported. Recording must never judge: writing a baseline exits 0, and nothing in the file may read as a verdict on the system.

4.2 · Data flow

Fig. 3 — A fingerprint's life. The two middle states both count as "unchanged" for the exit code; only the reason separates an acceptance from a suppression. The dashed path is the one the reason guards against: a finding that disappears without anyone having decided anything about it.

4.3 · How the data moves and transforms

diff() is where a baseline's reasons reach the findings. It sets two fields in place on every finding and builds the named list of what disappeared:

is_own_report (walk.py:379–394) matches a .json with "schema": "aisg/1" and "kind": "audit" or "inventory", or the SARIF run properties aisg_schema then own_output_skipped. A baseline (kind: audit-baseline) is deliberately not own output: it is walked.

4.4 · Decisions, and why

  • ⓐ--write-baseline renders first and always exits 0. It used to stop after building the report, so the skill's phase 1 needed two runs to get a report and a baseline of the same scan. Now both land from one run. Exit 0 because a survey that exits 1 would read as a failed step in CI or in the agent's loop, when it only recorded what exists. It refuses a target that is not an audit-baseline, and one that shares a path with -o — the second write would replace the first while stderr reported both.
  • ⓑA refresh carries reasons over, and drops the ones whose finding is gone. Rejected: start every refresh empty. Every acceptance would silently become a suppression again. Rejected too: keep every reason forever. A reason for a finding that no longer exists documents nothing and would later attach to a different finding with a colliding fingerprint. When both files hold a reason, the --baseline document wins, because the operator named it on that command line. Cost: a surprise if the two disagree; documented and tested.
  • ⓒA reason is required, and constrained. --accept exists only under --amend-baseline, so there is no way to add a reasoned acceptance without writing the reason. The checks come from two facts: the reason is printed as one line in every format (so: one printable ASCII line), and the baseline file is itself scanned (so: no secret shape, and no quoting of the literal that produced the finding). Verdict language is refused because a reason says why a finding stays, never that the system is fine.
  • ⓓ"No longer reported", never "fixed". A fingerprint disappears when the code is fixed, and also when the file moves or the snippet is reworded. The audit cannot tell those apart, so no renderer says more than it knows. The index block exists so that the gone fingerprint can at least be named by rule, file and title, instead of as sixteen hex characters.
  • ⓔOwn output is recognised by content, not by directory. Rejected: add .aisafe-audit/ to SKIP_DIRS. Measure and probe reports written there must be read as evidence (REPORTED <age>). For the same reason .gitignore never prunes .aisafe-audit/: ignoring it changes what git tracks, not what the next audit reads. Every skipped file is listed in inventory.own_output_skipped, so the skip stays visible.
  • ⓕActions are never defaults. write_baseline, inventory_only, list_rules, amend_baseline and accept are in main.NOT_CONFIGURABLE (main.py:72–74). A true in [tool.aisafe-audit] would make every run rewrite a baseline or run no rule, with no flag to switch it back off.

4.5 · For a scalable system

  • One JSON file per repository, merged by git. Two branches that each accept a finding produce a textual conflict in accepted and fingerprints. The file is written with sorted fingerprints, fixed key order and LF endings (_dump, baseline.py:331–340) to keep those conflicts small, but there is no merge tool. At dozens of accepted findings per team this is fine; at hundreds, a per-rule file would be.
  • The fingerprint is the only join key. Two findings that normalise to the same snippet share a fingerprint (STATUS.md, "Next" item 3), and now one reason accepts both. See recommendation 1.

4.6 · Security

  • The baseline is a trust boundary for the gate. Anything in fingerprints stops counting towards the exit code, reason or not. In this repository a test (test_committed_baseline_has_a_reason_for_every_fingerprint) makes a bare fingerprint fail CI. A user's repository has no such test, and the summary line does not count unreasoned entries. See recommendation 3.
  • The reason is operator input written into a scanned file. Hence the checks in ⓒ. The file is also re-read on every --baseline with the same checks, so a hand-edited reason cannot bypass them.
  • Refusals leave the file as it was. amend_baseline checks every accept before writing anything; _refreshed_baseline reads the target before the scan starts.

Key takeaways — the baseline

  • A fingerprint in the baseline is a suppression; a fingerprint with a reason is an acceptance. Only the second is a decision.
  • Reasons survive refreshes while their finding exists, and are dropped, with a count, when it does not.
  • Nothing says "fixed". A gone fingerprint is named, and the text admits a move looks the same.
  • The audit's own output is skipped by content and listed, so the loop in Fig. 1 does not feed on itself.

5 · S The five-phase skill

5.1 · Goal

Walk an owner from document 1 to document 2 with an agent that changes code only with per-row consent, decides each row from the JSON, and treats the re-audit — not its own diff — as the evidence. The previous document describes the skill's packaging (one canonical copy, two mirrors, the pinned bootstrap); this section is about the new procedure.

5.2 · Data flow

Fig. 4 — Phases and artefacts. Every command runs from the repository root, because [tool.aisafe-audit] resolves from the working directory. The recheck file is kind: audit, so the next walk skips it (ⓔ).

5.3 · How the data moves and transforms

The skill is prose, but it is prose that points at fields. The three branches of phase 3 map one-to-one onto the who values the renderer computes:

src/aisafe/skills/ai-safety-audit/SKILL.md:119–128 — three branches, decided by fieldsS
- `same_control: true`, the language is Python and the file is not a rule-4 file (`who:
  package`): offer the idiom from `references/apply/python.md` keyed by the first entry of
  `symbols`, quoting `leaves_open` verbatim from the JSON in the same message. ...
- `symbols` non-empty but `same_control: false`: state the rule's control first (from
  `references/controls.md`), then offer the package diff labelled
  "in addition to, not instead of: <leaves_open>". ...
- `mechanism: none`, or the language is not Python, or the file is a rule-4 file (`who:
  you` or `you, approval needed`): state the outside-package action. ...
src/aisafe/skills/ai-safety-audit/SKILL.md:151–153 — the evidence ruleS
Applying a diff is not evidence; the re-audit is. A fingerprint that is still reported
after the diff means the rule cannot see the control you wired -- say so, do not accept it
to make it go away. Stop after each row and ask whether to continue.

5.4 · Decisions, and why

  • ⓥOne row per approval, top-down, never skipping. A row is offered only when every row above it is applied, deferred "in so many words", or accepted with a reason. Rejected: batching, and letting the agent pick easy rows first. The table is in blast-radius order, so skipping ahead means fixing a logging gap while an ungated deploy tool stays open. Cost: forty-nine rows is forty-nine round trips; the VaiVia walkthrough (docs/handoff.md) stopped two rows into eleven.
  • ⓦThe JSON is the decision source, never the html or memory. The html is for people; its sentences can be rewrapped or reworded without a test noticing. recommendation.package is typed and validated. An agent that decides from prose decides differently on every host.
  • ⓧThe re-audit is the evidence. An agent can write a correct-looking diff that the rule cannot see (a gate wired through **cfg is the standard case; pydeep reports it as UNKNOWN). If the fingerprint is still there, that is a fact about the rule or the diff, and it is said out loud rather than accepted away.
  • ⓨThe skill proposes, it does not edit, the files that govern it. Whether .aisafe-audit/ is committed is asked, and the .gitignore line is shown as a diff. Protected paths get a restated, specific approval. The documents are the record; nothing the agent says in the conversation goes into them.

5.5 · For a scalable system

The ceiling is human attention, not compute. The audit of this repository takes seconds; a 49-row plan takes an afternoon of approvals. The upgrade path is already in the flow: acceptance with a reason is a first-class outcome, so an owner can close a whole class of rows in one sitting without the agent touching code. What is missing is a way to accept several fingerprints for one reason in one approval — --accept repeats, but the skill forbids batching.

5.6 · Security

  • The agent is the actor with write access, so its limits are the protected-path rule (hard rule 4) and one change per approval (hard rule 5). The plan marks protected rows you, approval needed, so the constraint is visible in the document, not only in the skill text.
  • Phase 5 can spend money. Tests, aisafe measure and aisafe probe may call model providers, so they wait for a separate approval; a non-loopback probe needs --i-have-authorization, which the user must add.

Key takeaways — the skill

  • Phase 3's three branches are the three values of the plan's who column; the agent reads fields, not sentences.
  • A diff proves nothing until the re-audit agrees. A finding that survives a fix is reported, not accepted.
  • The procedure is safe and slow. Its real ceiling is the number of approvals an owner will sit through.

6 · Cross-cutting: a fingerprint with a reason

The previous document described the fingerprint as the join key between runs. This work hangs a second value on it. One fingerprint now links: the finding in this run, its entry in the baseline's fingerprints, its index row (rule, file, title), its accepted reason, the finding's accepted_reason, the plan's status column and the "Remaining actions" group it lands in. Every renderer prints the reason: accepted: … in terminal and markdown, "Operator-recorded reason" in the html, accepted_reason in the JSON.

The question the flow was built to answer — what is still open, and who does it? — is one filter over the after-report:

shell — open rows from document 2's JSON, with what the package leaves openB
python -c "
import json
r = json.load(open('.aisafe-audit/audit-report-after.json'))
for f in r['findings']:
    if f['accepted_reason'] is None:
        p = f['recommendation']['package']
        print(f['id'], f['baseline_status'], p['mechanism'], p['same_control'], '|', p['leaves_open'])
print('no longer reported:', [g.get('rule') for g in r['baseline']['no_longer_reported']])
"

On this repository today (--baseline audit-baseline.json, run 2026-09-21): 22 findings, all 22 unchanged, all 22 with a reason, so the filter prints no open row. The plan's who column reads package 13 times, you 8 times and you, approval needed once — and "Rows the package can implement" is still empty, because accepted rows are not work. Ten of those thirteen are AUD-801 (guards with no measured profile), which is the package telling itself what to do next.

Key takeaways — cross-cutting

  • The fingerprint joins runs; the reason attached to it joins the audit to a human decision.
  • "What is left, and who does it" is a filter over one JSON file, not a reading of the html.

None of the previous document's recommendations was resolved by this work, so none was flipped there. Discovered while writing this one:

  1. Fingerprint collisions now carry a reason across findings. STATUS.md lists the collision (digits stripped from identifiers make ..._retriever and ..._retriever2 one fingerprint) as "harmless today". It stopped being harmless when reasons attached to fingerprints: one --accept now accepts both findings, and the second one shows the first one's reason. Fix before the VaiVia walkthrough records more acceptances: either add the evidence line's enclosing scope to the fingerprint payload, or make write_baseline refuse to write when two findings in one run share a fingerprint (cheap, and it surfaces the case instead of hiding it).
  2. The who column is not in the JSON. It is derived in html.py from inputs that are in the JSON, and SKILL.md restates the derivation in prose. That is two implementations of one rule, and the html's "the JSON is authoritative" claim is only true for the inputs. Emit who (and the resolved language) on each finding in the JSON, computed by the same _who, and let the skill read it.
  3. The gate does not distinguish an acceptance from a suppression outside this repository. A bare fingerprint stops counting just like a reasoned one, and the summary line (baseline: N new, N unchanged, N no longer reported) does not say how many had no reason. This repository is protected only by its own test. Add "N without a reason" to report._T_BASELINE, and consider a --fail-on-unreasoned flag for CI use downstream.
  4. "Remaining actions" groups by symbols, the plan by who. _remaining (html.py:1136–1138) puts any finding whose rule names a symbol under "Package control wired or available", including one in a .ts file that the plan marks you. The finding's own section adds the Python-only line, but the group heading still promises a package control. Group by the plan's who value instead, so the two sections of document 2 cannot disagree.
  5. The previous document's Fig. 3 caption is out of date. It says --write-baseline "short-circuits after build_report". Since c06d810 it renders the -o report first (decision ⓐ here). Add a one-line note under that caption pointing here; do not rewrite the old document.
  6. Accepted, because: the ten-box map cannot show two agents or two services separately. A per-unit map is the upgrade path, but the inventory's unit detection has not been tested on a real monorepo yet, and a wrong split is worse than a coarse picture that says what it is.

Key takeaways — next

  • The flow is built; it has been run end to end on nothing yet. Finishing VaiVia is the test.
  • Reasons made the fingerprint load-bearing, so a known collision moved from cosmetic to a correctness bug.
